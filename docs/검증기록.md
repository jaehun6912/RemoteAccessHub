## 3. 사용자 실행 기록 분석 (1.0.0, 2026-09-14 14:24~14:38)

사용자가 노트북에서 DDNS 주소로 공유기에 로그인하고, WOL 화면에서 [진단 내보내기]로 만든 파일을 분석했습니다.

### 실기기에서 확인된 동작

| 단계 | 결과 |
| --- | --- |
| DDNS 경유 공유기 화면 표시 | 성공 |
| 로그인 전 판정 | `-31998 Unauthenticated` → [PC 켜기] 비활성 |
| 로그인 성공 판정 | `session/login` 정상 직후 로그인 확정 → [PC 켜기] 활성 |
| 접힘·펼침 반복 중 세션 유지 | 약 5분 동안 로그인 상태 유지, 판독 불가를 로그아웃으로 취급하지 않음 |
| WOL 대상 매칭 | 버튼 후보 1개, 이름 일치 2개, 행 1개 → 대상 행의 버튼 선택 |
| 버튼 클릭 | 접근성 노드 클릭 성공 |
| 확인창 | "PC를 켜시겠습니까" 감지 → 화면 펼침 → 사용자가 확인 |
| 공유기 처리 | `wol/signal` 정상 응답, 요청 MAC이 대상 행의 MAC과 일치 |
| VPN 접속 | 이미 연결된 `HomeVPN`(예시 이름) 재사용 (재연결 시도 없음) |
| 작업 취소 2회 | 취소 보고, VPN 유지 |
| RDP | 내부 IP의 RDP 포트 응답 확인 후 `mstsc /f` 실행 |

WOL 요청 약 66초 뒤 내부 RDP 포트가 응답했습니다. 요청 전에 PC가 꺼져 있었는지는 로그로 알 수 없으므로 "실제 부팅 성공"은 사용자 확인이 필요합니다. 원격 데스크톱 로그인 성공 여부도 프로그램이 확인하지 않습니다.

### 실기기에서 드러난 문제와 1.1.0 수정

| 문제 | 원인 (진단 파일 근거) | 수정 |
| --- | --- | --- |
| 로그인 직후 공유기 화면이 바로 접혀 선택 화면을 가림 | 로그인 확정만으로 접었음. 실제로는 로그인 뒤 [관리도구]/[설정마법사] 선택 화면이 뜸 (사용자 제보) | 관리 화면(왼쪽 메뉴·로그아웃)이 보인 뒤에만 접음. 선택 화면이면 [관리도구] 자동 선택, 실패 시 펼친 채 안내 |
| [PC 켜기] 자동 이동 2회 실패 | 실제 주소가 경로 방식(`/ui/wol`)인데 해시 경로(`#/wol`)로 이동 시도 | 기본 경로 `/ui/wol`, 옛 설정 자동 변환. 앱 내부 경로 이동 → 메뉴 → 주소 직접 열기 순서 |
| 메뉴 클릭 대체 경로 실패 | 왼쪽 메뉴 스크롤 영역의 접근성 노드 위치가 모두 y=68로 잘못 보고됨. 그 위치를 눌렀음 | 메뉴는 위치가 정확한 장면 텍스트로 누름. 누르기 전 그 지점을 덮는 가장 작은 항목의 이름을 확인해 "로그아웃" 등 다른 항목이면 누르지 않음 |
| 열려 있던 WOL 화면의 목록이 오래됐을 수 있음 | 화면 재사용 | 화면의 [페이지 새로고침]을 눌러 `wol/show` 응답을 확인한 뒤 매칭 |
| 진단 파일에 DDNS 주소 노출 | 네트워크 기록의 경로와 로그 문장에 주소 마스킹 누락 | 경로·로그의 URL 호스트, 설정의 주소, IPv4 주소를 모두 가림 |

### 실기기 WOL 화면 구조 (매칭 규칙에 반영)

- 행은 `role=group` 노드이고 라벨이 "PC이름 MAC" 형식입니다.
- [PC 켜기] 버튼은 그 행 노드의 **자식**입니다.
- 1.1.0은 이 부모·자식 관계로 먼저 매칭하고(구조 매칭), 관계가 없을 때만 좌표 매칭을 씁니다.

## 5-5. 1.3.3 로그인 직후 커서가 안 보이는 문제

사용자 제보: "간혹 마우스 커서가 안 보임".

원인을 좁힌 근거:

| 확인 | 결과 |
| --- | --- |
| 사용자 답변 · 어디서 | RemoteAccessHub 창 위에서만 안 보임 |
| 사용자 답변 · 언제 | 공유기 로그인 직후 (보안문자 입력 후) |
| 사용자 답변 · 복구 | 창 밖으로 나가면 보임 |
| 이 PC의 Windows 설정 | "입력하는 동안 포인터 숨기기" **켜짐** (`SPI_GETMOUSEVANISH=1`), 포인터 자국 꺼짐 |
| 터치·펜 | 없음 (`SM_DIGITIZER=0`) → 터치 입력 뒤 시스템이 커서를 감추는 경우는 해당 없음 |

판단: 공유기 화면(WebView2)에 입력하는 동안 브라우저가 설정에 따라 커서를 숨긴다. 브라우저 창은 다른 프로세스지만 메인 창에 붙어 입력 상태를 함께 쓰므로 숨김이 메인 창 전체에 적용된다. 브라우저는 자기 화면 위에서 마우스가 움직여야 다시 보이게 하는데, 1.3.1부터 로그인이 확인되면 공유기 화면을 곧바로 높이 0으로 접기 때문에 그 기회가 없다. 다른 프로그램 창은 입력 상태를 공유하지 않아 거기서는 보인다. 세 가지 답변과 모두 맞는다.

### 1.3.5의 판단 (틀림)

처음 7회만 대조해 "직전 WOL 목록 요청(`wol/show`)이 끊긴 채 누르면 WOL 요청도 끊긴다"고 판단했습니다(끊김 3/3, 정상 2/2). 1.3.5는 누르기 전에 목록을 다시 불러오고, 끊기면 한 번 더 보내도록 바꿨고, 1.3.6은 사용자 요청으로 최대 5번으로 늘렸습니다.

사용자가 1.3.5·1.3.6으로 실행한 기록(WOL 요청 15회)에서 이 판단이 **틀렸음**을 확인했습니다.

| 관찰 | 횟수 |
| --- | --- |
| 목록 요청 정상(200) 뒤인데 WOL 요청 끊김 | 여러 번 (예: 22:59:06, 23:00:37, 23:01:50) |
| 목록 요청이 두 번 끊겼는데 WOL 요청 정상 | 여러 번 (예: 23:00:48, 23:02:08) |
| [확인] 뒤 결과까지 걸린 시간 | 정상 41~99ms, 끊김 60~118ms (겹침) |

1.3.5·1.3.6은 같은 틀린 판단 위에서 재시도만 늘린 것이었습니다.

### 공유기 화면 코드 분석

공유기 관리 화면 코드(`main.dart.js`, 이전에 저장해 둔 사본)에서 확인한 사실:

- WOL 켜기: 확인창 → "켜는 중" 표시 → `wol/signal` 요청을 기다림 → 잠시 뒤 표시 닫기. 요청 결과를 따로 확인하지 않음.
- 모든 공유기 API 호출이 한 함수를 거침: `fetch`로 보내고, 응답 본문을 끝까지 읽어 해석한 뒤, **`finally`에서 통신 객체를 닫음(`AbortController.abort()`)**. 시간 제한은 `wol/signal`에 쓰지 않음.
- 코드 전체에서 요청을 끊는 곳은 이 닫기뿐 → 페이지 이동이 없다면 `wol/signal`의 끊김은 **응답을 받은 뒤** 닫기와 브라우저 완료 처리가 겹친 결과로 추정.
- 기록에 `session/info`·`wol/show`도 자주 "실패"로 찍히는 것과도 맞음(모두 같은 함수 사용).

실험: 모의 공유기에서 같은 방식(본문을 다 읽고 곧바로 닫기)으로 요청 40건을 보냈을 때는 **40건 모두 정상 완료로 기록되어 재현되지 않았습니다.** 같은 PC 안 통신이라 겹칠 틈이 없었을 수 있습니다. 따라서 위 추정은 코드 근거만 있고 실기기에서 확인되지 않았습니다.

### 1.3.7 변경

| 변경 | 내용 |
| --- | --- |
| 기록 보강 | 끊긴 요청마다 공유기 응답(HTTP 상태)을 받았는지 남김: "200 받은 뒤 끊김(net::ERR_ABORTED)" / "실패(net::ERR_ABORTED)". 응답을 받은 경우 본문 판독도 시도 |
| 응답을 받은 뒤 끊김 | 공유기가 응답한 것이므로 결과로 삼음. 본문이 정상이면 처리 완료, 오류 코드면 오류, 본문을 못 읽어도 정상 상태 코드면 처리 완료로 보고 **다시 보내지 않음** |
| 응답 없이 끊김 | 1.3.6과 같음: 잠시 기다린 뒤 목록을 새로 불러와 처음 포함 최대 5번까지 보냄, 5번 모두면 "처리 여부 확인 불가" 주의 |
| 목록 요청 판정 | 응답을 받았으면 "끊김"으로 기록돼도 목록을 불러온 것으로 봄(불필요한 새로고침 줄임) |

| 검사 | 결과 |
| --- | --- |
| 응답(200)을 받은 뒤 끊김으로 기록된 WOL 요청(서버가 응답 후 연결을 열어 두고 페이지가 먼저 닫음, 실제 WebView2 기록 "200 받은 뒤 끊김") → 다시 보내지 않고 처리 완료, 공유기 수신 1회 | PASS |
